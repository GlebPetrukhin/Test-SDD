# Design

## Context

Основания: [proposal](proposal.md), [спецификация](../../../../sdd-specs/openspec/changes/compare-model-versions/specs/grid-models/spec.md), [общий design](../../../../sdd-specs/openspec/changes/compare-model-versions/design.md), [контракт 1.0.0](../../../../sdd-specs/contracts/grid-models-api.yaml), [кейсы QA](../../../../sdd-specs/openspec/changes/compare-model-versions/test-cases.md). Здесь определены только внутренние решения sdd-frontend.

Текущий `GridModelsComponent` хранит реестр и выбранную карточку через signals. `GridModelsService.list()` уже получает полные Model; отдельного метода GET карточки нет. `GridVersion.document` и `GridObject` содержат необходимые данные. Шаблон старого списка изменений читает `v.changes`, а вся секция версии находится под `@if (version())`.

## Decisions

### 1. Разделение расчёта, состояния и представления

Внутри `src/app/features/grid-models/` добавить:

| Файл | Назначение |
|---|---|
| `compare-model-versions.ts` | Чистая функция сравнения двух документов, без HTTP, Angular-компонентов и доступа к глобальному состоянию. |
| `version-comparison.types.ts` | Локальные типы пары, типизированных изменений полей, исключений и результата; это не сетевые DTO. |
| `version-comparison-state.ts` | Изолированное состояние одного экземпляра панели: выбор, доступность документов, запуск, получение данных и принадлежность результата запуску. |
| `version-comparison.ts`, `.html`, `.scss` | Standalone-компонент панели и представление локального состояния. |
| `compare-model-versions.spec.ts` | Unit-кейсы расчёта. |
| `version-comparison-state.spec.ts` | Unit-кейсы выбора документов и управления состоянием. |
| `tests/e2e/compare-model-versions.spec.ts` | Пользовательские кейсы QA с моками API. |

Дополнить существующий `GridModelsService` методом `get(id)` по контракту; подключить компонент в `grid-models.ts` и `.html`. Новый компонент размещается в карточке вне условия наличия отдельной версии, чтобы состояния модели без версий были доступны. Выбор единственной просматриваемой версии и выбор пары — разное локальное состояние.

Альтернатива — добавить расчёт и запросы прямо в существующий большой компонент. Выбрано выделение: так unit-кейсы расчёта и запоздавших завершений не зависят от формы загрузки и согласования. Отдельный глобальный store для этой функции не нужен.

### 2. Чистый расчёт и типы результата

Индексировать каждую сторону через Map и Set. Проверку пустого ID реализовать по явному набору Unicode White_Space из QA-кейса, без `trim()`. Значения и критерии равенства определены общим design; входы, массивы и поля `changes` не изменять.

Изменение — размеченное объединение added / removed / modified. Для modified использовать объединение изменений строковых полей, числового напряжения и последовательности связей, чтобы не смешивать типы значений. Отдельно хранить исключённые ID, количества пустых ID по сторонам и количество оставшихся объектов на каждой стороне. Последние счётчики позволяют различить отсутствие общих ID и отсутствие всех пригодных объектов.

Данные для показа формировать без копирования целых Model и повторной сериализации документов. Обход объектов и связей линейный по просмотренным элементам с учётом стоимости строк; массивы входа не сортировать. Для защиты от мутаций в unit-тестах замораживать входные фикстуры и проверять их сохранность.

### 3. Состояние выбора и загрузки

Хранить выбранные стороны как ссылки с `modelId` и `versionId`; не выводить идентичность из номера версии. Метаданные выбора отделить от кэша полных документов, ключ документа — `(modelId, versionId)`. Успешно загруженная Model наполняет этот кэш. Список options строится только для текущей модели; проверка перед запуском остаётся отдельной функцией, доступной unit-тестам.

Для асинхронного состояния использовать размеченные варианты idle / loading / ready / error / missing-versions; причины недопустимого выбора вычислять отдельно. При межмодельных ссылках сначала распознавать межмодельную пару, затем прочие причины недопустимости по согласованным сценариям. В состоянии ready хранить снимок идентификаторов и подписей сравниваемых версий вместе с результатом.

При отсутствии документов передавать загрузку в `GridModelsService.get(id)` с существующим таймаутом. Сетевые DTO не делать частичными: результат API остаётся полной Model. После ответа повторно разрешать обе версии по выбранным ID; отсутствие версии даёт отдельное состояние обновления выбора, а не пустой документ.

В панели предусмотреть действие обновления данных сравнения: сохранить метаданные и выбор, сделать кэш документов недоступным для нового запуска и получить Model. Оно даёт обычный пользовательский путь к повторному получению данных и позволяет воспроизвести кейсы ошибки загрузки без некорректных частичных ответов API или служебных переключателей в интерфейсе. При полном кэше обычное сравнение не запрашивает API повторно. Повтор после ошибки использует текущий выбор, а не снимок старой пары.

### 4. Защита от запоздавших завершений

Счётчик поколения увеличивать при смене модели, стороны, направления, принудительном обновлении данных, новом запуске и уничтожении панели. Каждый запуск захватывает своё поколение и пару. Любое завершение запроса или расчёта, включая catch и finally, обновляет состояние только для актуального поколения. Это защищает также путь A → B → A и не позволяет старому finally убрать индикатор нового запуска.

Смену выбора сразу отражать в signals и очищать результат/ошибку независимо от того, отменён ли предыдущий запрос. Отмена запроса может экономить ресурсы, но не заменяет проверку поколения. Unit-тесты управляют Promise загрузчика; нужны все сочетания успеха/ошибки и порядков завершения из QA-кейсов.

### 5. Представление и доступность

Выделить панель «Сравнение версий» с подписанными select «Было» и «Стало», действиями сравнения, смены направления и обновления данных. Отобразить пару независимо от наличия результата. Показать причины недопустимого выбора, загрузку, ошибку и повтор через доступные текстовые состояния; использовать обычную клавиатурную навигацию и объявление изменения состояния без принудительного перемещения фокуса.

Для изменённых полей показывать подписанные стороны. Число форматировать без фиксированного ограничения дробных знаков, скрывающего отличие; для строк сохранять пробелы, для links — порядок и повторы. Использовать Angular-интерполяцию, не вставлять исходные значения через HTML. Предупреждения, исключённые ID и количества пустых ID отображать независимо от списков различий. Для больших результатов раскрывать детали по объектам, чтобы не создавать сразу DOM для всех связей.

Существующий раздел «Изменения» остаётся связан с `Version.changes`. Новый результат хранится отдельно. Регрессия проверяет сохранность старого списка, issues и доступности действий согласования.

### 6. Проверки и порядок работы

Всего 34 кейса Front: 11 unit и 23 e2e. Их содержание — в хранилище; локальный tasks содержит по задаче с каждым ID. Для нового поведения сначала получить ожидаемое падение теста, затем реализовать соответствующий блок и получить зелёный результат. Случайная ошибка запуска или подготовки данных не считается требуемым красным результатом. Существующие регрессионные проверки могут быть зелёными сразу; намеренно ломать прежнее поведение не требуется.

E2E использует полные фикстуры контракта 1.0.0. Ошибки получения данных воспроизводятся через управляемый GET после обновления данных панели; таймаут — управлением временем браузера. Тесты состояния используют управляемые загрузчики, не ожидания реальной сети. Сохранить запуск прежнего набора `grid-models.spec.ts`; добавить проверку доступности новой панели существующим AxeBuilder как техническую проверку.

## Risks / Trade-offs

- Объём связей, строк и истории Model не ограничен лимитом объектов. Предварительный [эксперимент](../../../docs/experiments/compare-model-versions-benchmark-results.json) не измеряет Angular и DOM. Проверить приложение в браузере на больших результатах; при наблюдаемой блокировке перенести расчёт в порции или worker внутри Front. Если проблема в объёме ответа API, поднять вопрос владельцу хранилища и бэку, не менять контракт локально.
- Отсутствует согласованный числовой норматив отзывчивости. Записать условия и фактические измерения, не выдавать локальный порог за критерий PO/QA.
- Два режима сравнения могут визуально смешаться. Использовать отдельную панель, отдельное состояние и регрессионные кейсы QA.
- Общая карта `tasks.md` в хранилище на момент планирования ещё отсутствует. Локальный план является входом для неё; создавать карту и отмечать чужие задачи из Front нельзя. Это не мешает подготовить собственные задачи по уже доступным design и кейсам.

## Развёртывание (Kubernetes)

Миграций, новых переменных окружения, портов, томов и изменений deploy не требуется. Выпуск — обычная сборка фронта с существующим проксированием.
