# Заключение Front по стыку: compare-model-versions

Дата: 2026-10-27.

Статус: со стороны Front принят предложенный вариант вычисления сравнения на клиенте с использованием уже загруженных документов и сохранением контракта 1.0.0. Это заключение одного участника; общий design, повторное ревью QA, тест-кейсы и готовность реализации им не подменяются. Отзывчивость вычисления оценена предварительно; приёмка интерфейса в браузере ещё не проводилась.

Предыдущие замечания Front учтены: базовые правила подтверждены PO; состав сравниваемых полей и незначимость порядка объектов определены; недопустимый выбор объясняется пользователю; ошибка, повтор и принадлежность результата текущей паре описаны. Дополнительных продуктовых уточнений от Front для согласования предлагаемого стыка нет. Это не отметка прохождения QA-ревью.

## Что подтверждает Front

1. Сравнение выбранной пары вычисляется на фронте. По контракту Model содержит версии с полным `document.objects`; текущие типы `GridModel`, `GridVersion`, `GridObject` уже представляют эти данные. Новое сетевое представление результата не требуется.
2. Источник — успешно полученная Model текущей модели. Допустимо использовать документы из уже загруженного ответа существующего API, если обе выбранные версии и их полные документы присутствуют. Обязательный запрос при каждом сравнении не нужен: содержимое сохранённых версий неизменяемо. Это разрешение относится к содержимому документов, а не к актуальности статусов и разрешений на действия.
3. При необходимости получения данных используется существующий `GET /api/grid-models/{id}`. В текущем `GridModelsService` отдельного метода чтения карточки ещё нет; его добавление будет внутренней работой Front по действующему контракту. Сейчас `list()` уже загружает Model с документами. Отсутствующий документ не заменяется пустым, отсутствие версии после успешной загрузки требует обновить данные и выбор согласно предложению бэка.
4. Пара определяется `(modelId, beforeVersionId, afterVersionId)`. Номер версии, положение в массиве и `baseVersionId` не заменяют идентификатор версии. Фронт проверяет допустимость и завершённость выбора до запуска сравнения.
5. `Version.changes` используется только для прежнего сравнения при загрузке. Новая функция читает `Version.document`, не изменяет документы, статусы, ревизию, журнал и прежние правила сравнения.
6. Ошибка получения данных отображается как «Не удалось выполнить сравнение» с действием «Повторить» для текущей допустимой пары. Таймаут запроса — прежние 10 секунд. Отсутствие изменений и неполнота результата не используются вместо ошибки загрузки.
7. Смена модели, любой версии или направления сразу убирает прежние результат и ошибку. Запоздавшие успех, ошибка и завершение старой операции не меняют состояние текущего запуска. Одной проверки совпадения тройки недостаточно при переходе A → B → A: Front обеспечит различение запусков. Конкретный механизм относится к локальному design Front.

## Правила интерпретации данных, принимаемые Front

- Непустые ID, название и тип сравниваются точно, с учётом регистра, без обрезания пробелов и нормализации. Для отображения сохраняются исходные значения.
- Пустой ID — строка нулевой длины либо строка только из Unicode White_Space. Для общего design предлагается явно закрепить набор: U+0009–U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000–U+200A, U+2028–U+2029, U+202F, U+205F, U+3000. Проверка не изменяет исходную строку. U+FEFF и U+200B в этот набор не входят; обычный `trim()` не является определением согласованного набора.
- Напряжение сравнивается как полученное JSON-число без допуска; `110` и `110.0` равны. Отображение не должно округлением скрывать обнаруженное различие. Сохранение исходной текстовой записи JSON-числа контрактом не предусмотрено.
- Связи сравниваются по длине, значениям и позициям. Порядок и повторы сохраняются; сортировки и преобразования во множество нет.
- Для пустых ID считаются исключённые объекты отдельно по каждой версии. Повторы остальных ID находятся отдельно в каждой версии; объединение повторяющихся ID исключается из обеих версий. Список исключённых ID содержит каждый такой ID один раз.
- Оставшиеся ID только в «Стало» дают добавления, только в «Было» — удаления, в обеих версиях — сравнение `name`, `type`, `voltageKv`, `links`. Непересекающиеся уникальные ID дают добавления и удаления; общий ID для результата не обязателен.
- Порядок объектов, метаданные и `issues` не определяют различия или полноту результата. Ошибки типа, напряжения и ссылок не препятствуют сравнению сохранённых значений при однозначном ID.
- «Различий нет», «В однозначно сравнимой части различий нет» и «Нет объектов для однозначного сравнения» остаются разными состояниями согласно спецификации; предупреждения и сведения об исключениях сохраняются.

## Предварительная оценка отзывчивости

Проведён отдельный эксперимент, который не подключён к приложению и не является реализацией фичи или автотестами QA. Он индексирует объекты по ID и сравнивает поля и последовательности связей без сортировки. Ожидаемый объём работы зависит от объектов, просмотренных связей и длины строк; повторное сравнение не требует обходить историю всех версий. Результат хранит ссылки на значения полей, без глубокого копирования документов.

[Воспроизводимый эксперимент](experiments/compare-model-versions-benchmark.mjs), [исходные результаты](experiments/compare-model-versions-benchmark-results.json). Запуск из `sdd-frontend`: `node docs/experiments/compare-model-versions-benchmark.mjs`.

Среда: Windows, Node.js v24.22.1, Intel Core i3-1215U. Для каждой нагрузки — две версии по 1000 объектов, 10 прогревочных и 40 измеренных сравнений уже разобранных JSON-документов. Проверены одинаковые документы и изменение всех четырёх полей каждого объекта; изменение последней связи заставляет просматривать всю последовательность.

| Связей на объект в каждой версии | p95 вычисления, одинаковые / изменённые | Размер JSON пары | Медиана разбора JSON пары, одинаковые / изменённые |
|---|---|---|---|
| 8 | 1,08 / 1,14 мс | 0,34–0,35 МБ | 1,08 / 1,01 мс |
| 100 | 1,13 / 1,10 мс | 2,54–2,56 МБ | 7,97 / 8,80 мс |
| 1000 | 9,92 / 7,20 мс | 25,94–25,95 МБ | 93,91 / 148,58 мс |

Для рассмотренных нагрузок вычисление на клиенте приемлемо как выбранный способ реализации пилота. Последняя строка — искусственная нагрузка, превышающая прежний лимит тела загрузки 2 МБ для каждой версии; она не объявляется новым поддерживаемым размером документа.

Границы вывода: измерен Node.js, а не браузер с Angular; не измерены сеть, полная история Model, память приложения, отрисовка полей и слабые устройства. Лимит 1000 объектов не ограничивает суммарный объём строк, связей и истории. Поэтому безусловное обещание отзывчивости для любого ответа 1.0.0 не даётся и числовой норматив приёмки этим заключением не вводится.

При реализации Front отдельно проверит браузер на согласованных данных, включая длинные связи и большой результат. Выбор порционной обработки, фонового вычисления и способа отображения больших списков остаётся за Front. Если узким местом окажется получение всей Model, потребуется совместное обсуждение отдельного получения документов или серверного сравнения; такой API сейчас не запрашивается и не утверждается.

## Передача следующему участнику

Со стороны Front препятствий к оформлению общего design по предложенному варианту нет. Для владельца хранилища подтверждены клиентское вычисление, повторное использование загруженных документов, разделение нового результата и `Version.changes`, правила ошибок и запоздавших ответов. Front согласен оставить контракт 1.0.0; сам контракт не изменялся.

Владелец хранилища фиксирует общий стык с учётом заключений участников. Повторное ревью и тест-кейсы остаются за QA. После фиксации стыка и появления кейсов Front создаёт локальное изменение `compare-model-versions-front` с указателем, внутренним design и задачами по своим кейсам. Отметки согласования других участников, общий design, кейсы и план бэкенда в этом ревью не создавались.
