Дата: 2026-10-27.

[Общий design](../../sdd-specs/openspec/changes/compare-model-versions/design.md) перенесён в sdd-specs по поручению пользователя; повторное ревью QA и готовность к реализации не подтверждены.

Ниже сохранён исходный текст предложения для истории. Формулировки о необходимости согласования в нём относятся к состоянию до подтверждения пользователя; действующие договорённости изложены в общем design изменения в sdd-specs.

## Предлагаемое решение и альтернатива

Предлагаем сохранить API без изменений, версия 1.0.0. Источник данных — `GET /api/grid-models/{id}`: ответ Model содержит `versions`, а каждая Version — исходный `document.objects`, идентификатор, номер и статус. Документы уже доступны независимо от статуса версии; операция скачивания опубликованной версии для этой функции не нужна.

Предлагаем вычислять отдельное сравнение выбранной пары на фронте по полученным документам. Это требует согласия владельца фронта: бэкенд не назначает ему реализацию и не определяет его внутренние типы, компоненты или алгоритмы.

Основание: новый ответ сервера не нужен для получения значений «было → стало», повторяющихся ID, пустых ID и порядка связей. Содержимое сохранённой версии неизменяемо. Документ ограничен 1000 объектами, но общее число версий модели и суммарное число связей этим лимитом не ограничены; отзывчивость интерфейса должен оценить владелец фронта.

Альтернатива — отдельная операция сравнения на сервере. Она уместна, если фронт не принимает вычисление на клиенте или требуется единый серверный результат для других потребителей. Тогда отдельно согласуются операция, идентификаторы модели и двух версий, типизированные изменения полей, сведения об исключениях и ошибки; контракт расширяется с повышением версии. Такой endpoint и его формат этим документом не утверждены.

## Распределение ответственности для предлагаемого варианта

| Участник | Предлагаемая ответственность |
|---|---|
| Бэк | Передавать сохранённые документы без исправления значений и порядка массивов; сохранять доступность документов всех статусов, прежний формат ошибок и прежнее сравнение при загрузке. Проверить это по кейсам, которые подготовит QA. |
| Фронт, после подтверждения владельца | Выбор пары, проверка её допустимости, вычисление отдельного сравнения, показ полей и неполноты, обработка ошибок получения данных и защита от запоздавших результатов. |
| Бэк и фронт совместно | Принять место вычисления, правила интерпретации переданных данных и порядок работы с загруженными документами; согласовать общий design. |
| QA | Повторно проверить уточнённые требования и стык, подготовить кейсы и определить владельцев автоматизации. |
| Владелец хранилища | Внести согласованный стык в общий design изменения; обновлять контракт при его фактическом изменении. |

## Данные и совместимость

1. Пара определяется тройкой `(modelId, beforeVersionId, afterVersionId)`. Обе версии берутся из `versions` одной Model; идентификатор версии не заменяется номером, индексом массива или `baseVersionId`.
2. Документы читаются из `Version.document`, а не из `Version.changes`. Поле `changes` остаётся результатом прежнего сравнения с базовой опубликованной версией и не является результатом произвольной пары.
3. Название, тип, напряжение и связи берутся из `name`, `type`, `voltageKv`, `links`. Неизвестный тип, неположительное напряжение и несуществующие ссылки передаются и сравниваются как сохранённые значения; список `issues` не является признаком неполноты сравнения.
4. Метаданные версии нужны для обозначения пары, но не участвуют в определении различий. Новая функция не записывает документы, статусы, ревизию или историю действий.
5. Новый сетевой формат результата сравнения для предложенного варианта не вводится. Внутреннее представление результата относится к ответственности фронта.

## Правила сравнения для совместного подтверждения

Следующие технические уточнения предлагаются для общего design; они не меняют подтверждённые PO сценарии.

- Непустые ID и строковые значения сравниваются точно, с учётом регистра, без обрезания пробелов и нормализации. Например, `line-1` и `LINE-1` — разные ID. Исходные значения сохраняются для отображения.
- Для распознавания ID, состоящего только из пробельных символов, предлагается согласовать набор Unicode White_Space; строка нулевой длины также считается пустым ID. Это правило требует совместного подтверждения, чтобы языковые функции обработки пробелов не давали разных результатов.
- Напряжение сравнивается как JSON-число без допуска: `110` и `110.0` равны. Округление при показе не должно скрывать обнаруженное различие.
- `links` сравнивается как последовательность строк: значимы длина, значения и позиции элементов. Сортировка и удаление повторов перед сравнением не выполняются.
- Пустые ID исключаются с отдельным количеством объектов для каждой версии. Повторения остальных ID определяются отдельно в каждой версии; объединение таких ID исключается из обеих версий. Перечень исключённых ID не содержит повторов.
- Среди оставшихся объектов ID только в «Стало» означает добавление, только в «Было» — удаление, в обеих версиях — сравнение четырёх полей. Разные непересекающиеся наборы уникальных ID дают добавления и удаления, а не сообщение об отсутствии объектов для сравнения.
- Если исключений нет и различий нет, используется «Различий нет». При исключениях и отсутствии различий в оставшейся части — «В однозначно сравнимой части различий нет». Если после исключений в обеих версиях вообще не осталось объектов — «Нет объектов для однозначного сравнения». Предупреждения и сведения об исключениях сохраняются по spec.

## Получение данных, ошибки и смена пары

Предлагаем разрешить использовать уже успешно загруженную Model, если в ней есть полные документы обеих выбранных версий. Неизменяемость содержимого версии позволяет повторно сравнивать эти документы без обязательного запроса при каждом запуске. Если нужных документов нет, требуется успешное получение Model; отсутствие данных не трактуется как пустой документ или отсутствие различий. Если выбранной версии нет и в полученной Model, сравнение не выполняется, пользователю предлагается обновить данные и выбор.

GET возвращает существующий ответ `200 Model` либо ошибку `{code, message}`. В реализации для отсутствующей модели используется `404 not_found`, для недоступного хранилища — `503 unavailable`. Новые коды ошибок не предлагаются. Успешный ответ с ошибками проверки объектов остаётся успешным получением данных.

При сетевой ошибке, таймауте или ошибке API во время получения данных выбранной пары пользовательское сообщение — «Не удалось выполнить сравнение», действие — «Повторить» по [grid-models-29]. Повтор относится к текущей допустимой паре. Сохраняется ранее согласованный предел ожидания UI-запроса 10 секунд.

При изменении модели, любой версии пары или направления старые результат и ошибка убираются. Полученный позднее ответ или ошибка предыдущего запуска не подменяет состояние текущего выбора, включая возврат пользователя к ранее выбранной паре. Способ обеспечения этого поведения выбирает фронт.

При недопустимом или незавершённом выборе сравнение и получение данных ради него не запускаются; используются причины из [grid-models-24]–[grid-models-27]. Это не меняет обычную загрузку карточки модели. При предложенном варианте сервер не получает выбранную пару и не может проверять её как аргументы отдельной API-операции.

## Прежнее сравнение и развёртывание

Сравнение при загрузке остаётся отдельным поведением: порядок связей игнорируется, при повторяющемся ID используется первый объект. Поле `Version.changes`, правила загрузки и переходы статусов не переопределяются новым сравнением. Это необходимо проверить по [grid-models-31] и [grid-models-32].

Для предлагаемого варианта новые переменные окружения, порты, тома и сервисы не требуются. Доступ к API остаётся по относительным путям `/api/...`.

## Что осталось согласовать

- Владелец фронта: принять либо отклонить вычисление на клиенте и использование уже загруженных неизменяемых документов; оценить объём данных и отзывчивость.
- Бэк и фронт: подтвердить точные сравнения строк и чисел, обработку пробельных ID, последовательностей связей и запоздавших результатов.
- QA: повторно проверить обновлённые требования и предложенный стык. Историческое `qa-review.md` не изменяется бэкендом и не считается закрытым без QA.
- После согласования: владелец хранилища фиксирует общий design и итоговую версию контракта, QA готовит кейсы, затем владельцы приложений планируют свои локальные изменения. ID кейсов и согласование других участников в этом предложении не назначаются.
