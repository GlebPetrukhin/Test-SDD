## Decisions

### Проверка существующего серверного поведения

Основная работа — интеграционные тесты существующего приложения. Новый обработчик сравнения, отдельные DTO результата и серверный алгоритм произвольной пары не планируются. `GridModelsEndpoints`, `GridContracts`, `GridStore` и `GridRules` изменяются только при воспроизводимом отклонении от согласованных требований после добавления соответствующего теста.

Существующий `GridRules.Diff` остаётся реализацией прежнего сравнения при загрузке. Не заменять его новым алгоритмом и не пересчитывать ранее сохранённые `Changes` при GET. Проверка вычисления нового сравнения относится к другой стороне и в этот локальный план не входит.

### Организация интеграционных тестов

Кейсы размещаются в `tests/integration/CompareModelVersionsTests.cs`. Каждый кейс получает отдельный тест с `[Fact(DisplayName = "[<кейс>] …")]`, `Trait("Scenario", "<сценарий>")` и `Trait("TestCase", "<кейс>")`. Варианты одного кейса могут выполняться внутри одного теста, не создавая фиктивных ID в исходниках.

Используется существующая `GridFixture` с отдельной PostgreSQL-схемой и `WebApplicationFactory<Program>`. Данные и операции подготовки выносятся в `tests/integration/GridComparisonData.cs`: каждый тест получает собственную модель, состояние не заимствуется у соседнего теста. Изменения общего вспомогательного кода не должны ломать существующие `GridModelsTests`.

Для кейсов чтения разрешается подготовить точное сохранённое состояние через `GridStore.Execute(..., write: true)` в тестовом окружении. Это позволяет задать требуемые метаданные и статусы, не выдавая подготовку данных за проверку реальных переходов. Значения фикстуры не добавляются в production-справочники организаций. Для кейсов загрузки и запрета submit проверяемые действия выполняются через HTTP API.

Поля и массивы проверяются в ответе HTTP с сохранением длины, порядка и значений. Для неизменности чтения дополнительно сравниваются снимки JSON-состояния PostgreSQL до и после запросов, без зависимости от порядка ключей JSON-объекта. Сравнение ответа с самим собой или проверка только статуса 200 недостаточны.

### Проверка ошибок и изоляция

Для проверки 404 используется гарантированно отсутствующий ID модели. Для 503 поднимается отдельный тестовый экземпляр приложения с изолированной заведомо недоступной строкой подключения и коротким таймаутом. Общая PostgreSQL других тестов, контейнеры и демонстрационный стенд не останавливаются.

Запуск возможен с существующим `GRID_TEST_CONNECTION` и доступной тестовой БД либо через текущий `tests/compose.yaml`. Новые параметры production, миграции и изменения Kubernetes не нужны.

### Решение по коду отказа submit

Для [grid-models-28.1] пользователь подтвердил `409 invalid_transition`; решение записано в [BACK-01](review-notes.md). Кейс хранилища уже содержит это ожидание. Текущая реализация возвращает `400 validation`, поэтому требуется целевое исправление `GridRules.Act` после падающего интеграционного теста.

Исправление ограничено отказом submit версии draft с непустым issues после существующих проверок организации и revision. Статус, документы, issues, revision и events при отказе сохраняются. Общий метод `Invalid(...)` не меняется: он обслуживает и другие ошибки. Коды прочих ошибок и проверки approve/publish сохраняются. Контракт OpenAPI 1.0.0 уже допускает ответ 409 и Error с code; его схема не изменяется.

### Порядок выполнения

Сначала пишется и запускается тест по кейсу, затем при необходимости исправляется серверное поведение. Если новый тест сразу подтверждает существующую реализацию, искусственно ломать приложение или добавлять функциональность не требуется. После каждого изменения выполняется соответствующий тест и затронутый регресс. Все задачи остаются незавершёнными до фактической проверки.

## Risks / Trade-offs

- Подготовка через хранилище может скрыть ошибку загрузки: для кейсов прежнего сравнения создание версии выполняется через POST, а чтение проверяется отдельным GET.
- Произвольные изменения сериализации или нормализация массивов способны нарушить выдачу данных: проверки выполняются на границе HTTP и включают ошибки сохранённых объектов.
- Исправление общего участка проверок issues может случайно изменить коды других действий: ограничить изменение условием submit и проверить существующий регресс. Решение по коду принято, его реализация ещё не подтверждена.
- Сверка прослеживаемости на этапе планирования ожидаемо сообщает об отсутствующих автотестах и локальном плане фронта. Строгая сверка без ошибок является условием последующей проверки реализации, а не уже достигнутым результатом.
