# Proposal

## Why

Пользователю нужно понимать, как изменились данные модели между двумя выбранными версиями, в том числе неопубликованными. Сравнение только с базовой опубликованной версией и список изменённых объектов не позволяют увидеть конкретные значения полей до и после изменения.

## What Changes

- Пользователь выбирает любые две различные сохранённые версии одной модели независимо от их статусов и наличия опубликованной версии.
- Пользователь явно задаёт направление сравнения: версия «Было» и версия «Стало».
- Результат показывает добавленные, удалённые и изменённые объекты; для изменённых — названия изменившихся полей и значения «было → стало».
- Объекты сопоставляются по ID. Сравниваются название, тип, напряжение и связи. Смена ID означает удаление старого объекта и добавление нового. Порядок самих объектов и метаданные версий не участвуют в сравнении.
- Порядок связей объекта значим: перестановка тех же связей считается изменением поля и показывается как «было → стало».
- Если повторяющиеся ID не позволяют однозначно сопоставить часть объектов, система показывает однозначно определяемые различия, предупреждает о неполном результате и указывает исключённые ID. Отсутствие различий в проверенной части не означает отсутствия различий во всей модели.
- Объекты с пустыми или состоящими только из пробелов ID также исключаются с предупреждением о неполноте и количеством исключённых объектов по каждой версии. Другие ошибки проверки не мешают сравнению сохранённых значений однозначно определяемых объектов и сами по себе не делают результат неполным.
- Сравнение не запускается при недостаточном числе версий, незавершённом выборе, выборе одной версии дважды или версий разных моделей; причина объясняется пользователю.
- При ошибке получения данных показываются ошибка и повтор действия. Результат всегда относится к явно указанной выбранной паре; при смене пары старый результат убирается.
- Затронуты sdd-frontend и sdd-backend. По согласованному design фронт вычисляет отдельное сравнение из исходных документов, бэк выдаёт сохранённые данные и сохраняет прежнее сравнение. Контракт без изменений, версия 1.0.0; новый API сравнения не вводится.
- По уже принятому решению BACK-01 уточняется ответ на submit ошибочного draft с актуальной revision и существующей организацией: 409 invalid_transition без изменения состояния. Кейс QA [grid-models-28.1] сохраняется; тест и исправление выполняет бэк в своём локальном изменении.
- Сравнение при загрузке с базовой опубликованной версией сохраняет прежнее поведение: перестановка связей не считается изменением, при повторяющемся ID используется первый объект. Новые правила сравнения выбранной пары на него не распространяются.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `grid-models`: сравнение произвольно выбранных версий одной модели с детализацией изменений полей.

## Impact

Продуктовые решения PO внесены в требования и сценарии приёмки; общий стык согласован бэком и фронтом в design.md, контракт остаётся версии 1.0.0. QA подготовил 50 кейсов и отразил повторное ревью требований и стыка в test-cases.md. Оба приложения создали локальные планы, общая карта находится в tasks.md. Завершение ревью кейсов владельцами, реализация, фактические прогоны, приёмка и архивация отслеживаются отдельно; наличие плановых документов не подтверждает выполнение работ.

## Out of scope

Сравнение разных моделей, объединение версий, редактирование из результата сравнения, экспорт отчёта, изменение допустимых переходов согласования и публикации, изменение либо унификация прежнего сравнения при загрузке и изменение правил проверки загружаемых данных. Единственное уточнение ответа отказа submit — уже принятое BACK-01; оно не разрешает согласование ошибочной версии и не переопределяет ошибки остальных действий.

## Решения PO по уточнениям команды

PO подтвердил предложенный набор уточнений и сохранение прежнего сравнения при загрузке в рамках этой задачи. Решения ниже отражены в дельте spec; ранее предложенные сопоставление по ID, направление и явное отсутствие различий теперь подтверждены.

| Замечание | Решение PO и сценарии |
|---|---|
| QA-01 / фронт: статус базовых правил | Сопоставление по ID, направление «Было → Стало» и явное отсутствие различий подтверждены; [grid-models-09], [grid-models-13], [grid-models-14]. |
| QA-02 / фронт: состав данных | Название, тип, напряжение, связи; порядок объектов и метаданные версий не учитываются; смена ID = удаление и добавление; [grid-models-11], [grid-models-12], [grid-models-17]–[grid-models-21]. |
| QA-03 / фронт: недопустимая пара | Выбор ограничен версиями одной модели; недопустимая или незавершённая пара не сравнивается, причина отображается; [grid-models-24]–[grid-models-27]. |
| QA-04: ошибки сохранённых данных | Неизвестный тип, недопустимое напряжение и несуществующие ссылки не препятствуют сравнению сохранённых значений при однозначном ID; [grid-models-28]. |
| Бэк: пустой ID или только пробелы | Объекты исключаются с предупреждением о неполноте, указанием версии и количества; [grid-models-22], [grid-models-23]. |
| QA-05 / фронт: ошибка и принадлежность результата | Ошибка с повтором для текущей выбранной пары; старый результат убирается при смене пары; [grid-models-29], [grid-models-30]. |
| Бэк: прежнее сравнение при загрузке | Поведение сохраняется, новые правила на него не распространяются; [grid-models-31], [grid-models-32]. |

Исходные замечания QA сохранены в `qa-review.md` как историческое ревью до уточнений. Актуальный результат повторного QA-ревью требований и стыка отражён в Gaps файла `test-cases.md`; кейсы подготовлены для ревью владельцами приложений. Это не приёмка реализации и не подтверждение зелёных автотестов.

Дополнительное принятое решение BACK-01 отражено в общем design и кейсе [grid-models-28.1]. Основание — `sdd-backend/openspec/changes/compare-model-versions-back/review-notes.md`: пользователь подтвердил 409 invalid_transition, блокировка уточнения снята, исправление ещё не выполнено.

## Следующий этап и владельцы

- Владельцы бэка и фронта завершают ревью подготовленных QA кейсов; замечания и решения фиксируются явно. Распределение 16/34 кейса определяется полем Automation.
- Реализация и автотесты выполняются владельцами по уже созданным локальным планам `compare-model-versions-back` и `compare-model-versions-front`; подробные задачи остаются в приложениях.
- Владелец sdd-specs ведёт общую карту tasks.md по фактическим результатам, включая исправление BACK-01, проверку стенда и закрытие локальных изменений.
- QA проверяет результат на стенде; PO принимает его по согласованным пользовательским сценариям. Затем выполняются строгая сверка и архивация в установленном порядке.
