# Test Cases

Изменение: `compare-model-versions`. Основания: дельта `specs/grid-models/spec.md`, согласованный `design.md`, `contracts/grid-models-api.yaml` версии **1.0.0**. Кейсы подготовлены для ревью владельцами приложений; выполнение и наличие автотестов этим документом не подтверждаются.

Бэк проверяет выдачу исходных документов и прежнее сравнение при загрузке. Отдельного API сравнения нет: выбор пары, вычисление и представление результата принадлежат фронту. В Coverage указаны проверки каждой стороны; фронтовые сценарии выбора и направления не требуют выдуманных серверных проверок пары.

Общие данные и условия (применяются, если кейс не переопределяет их):

- Объекты задаются JSON без сокращения полей: `B1={"id":"bus-1","name":"Шина 1","type":"busbar","voltageKv":110,"links":[]}`, `B2={"id":"bus-2","name":"Шина 2","type":"busbar","voltageKv":110,"links":[]}`, `L={"id":"line-1","name":"Линия 1","type":"line","voltageKv":110,"links":["bus-1","bus-2"]}`. Запись `L{voltageKv:220}` означает копию L с заменой только указанного поля; это описание тестовых данных, а не формат API.
- `D110={"objects":[B1,B2,L]}`, `D220={"objects":[B1,B2,L{voltageKv:220}]}`, `D330={"objects":[B1,B2,L{voltageKv:330}]}`. Порядок элементов задан явно.
- Модель A: `id=model-a`, `name=Сеть Урал`, `region=Урал`, `ownerId=ural`, `revision=7`, `publishedVersionId=v-a4`. Версии: `(id,number,status,baseVersionId,document)` = `(v-a1,1,draft,null,D110)`, `(v-a2,2,review,null,D220)`, `(v-a3,3,approved,null,D330)`, `(v-a4,4,published,null,D110)`, `(v-a5,5,rejected,v-a4,D220)`. Остальные обязательные поля Version: `title=Версия N`, `organizationId=ural`, `createdAt=2026-10-27T00:0N:00Z`, `issues=[]`, `changes=[]`; для rejected есть событие возврата с комментарием «На доработку». `events` содержит подготовленную историю, которая не меняется от чтения и сравнения.
- Модель B: `id=model-b`, `name=Сеть Восток`, `region=Восток`, `ownerId=ural`, `revision=1`, `publishedVersionId=null`, версия `v-b1`, `number=1`, `status=draft`, `baseVersionId=null`, `document=D330`; остальные обязательные поля как выше. Организация `ural` существует; в кейсе 20 также существует `qa-org`.
- В integration — PostgreSQL с изолированными данными, подготовленными в состоянии кейса. Логические имена model-a/v-a1 обозначают ID фикстур; если ID генерирует API, подставить фактически возвращённые ID. GET возвращает `200 Model`, если кейс не задаёт ошибку. Создание версии: `POST /api/grid-models/{id}/versions`, тело `{title,baseVersionId,revision,organizationId,document}`; `201 Model`. Действие: `POST /api/grid-models/{id}/versions/{versionId}/actions`, тело `{action,revision,organizationId,comment}`. Перед записью брать текущую revision. Подготовка данных не является шагом отдельного сравнения.
- В e2e — API замокан по контракту, карточка модели открыта. Полный ответ Model содержит все обязательные поля; отличия документа/статуса/ошибок указаны в кейсе. Для проверки получения недостающих данных состояние пары сохраняется, полных документов ещё нет; управляемый ответ `GET /api/grid-models/model-a` выдаётся после запуска. Когда полные документы уже есть, новый GET при каждом сравнении не требуется.
- В unit проверяется наблюдаемый результат вычисления или выбора без привязки к классам, структуре внутреннего результата и элементам UI. Пути Automation обозначают репозиторий и набор тестов; конкретные файлы выбирает владелец приложения.
- Для неполного результата проверять отсутствие самостоятельного сообщения «Различий нет»; оно не тождественно фразе «В однозначно сравнимой части различий нет». Предупреждения: `Wdup=Результат сравнения неполный: есть объекты с повторяющимися ID`, `Wempty=Результат сравнения неполный: есть объекты с пустым ID`.

### [grid-models-09.1] Документы версий всех статусов — API

- **Preconditions**: Подготовлена модель A с пятью статусами и разными базами.

## Gaps

Непокрытых сценариев дельты нет. Уточнения QA-01–QA-05 из исторического qa-review.md отражены в актуальных proposal, spec и design; этот вывод относится к повторному QA-ревью требований и стыка, а не к приёмке реализации.

Точные тексты серверных issues и предложения обновить выбор после отсутствия выбранной версии в успешном Model не установлены: проверяется смысл и доступность действия, новые обязательные строки в кейсах не вводятся. Измеримый норматив отзывчивости клиентского расчёта отсутствует; порог производительности этим набором не задаётся.

Актуализация владельцем хранилища: локальные планы `compare-model-versions-back` и `compare-model-versions-front` уже созданы; общая карта находится в `tasks.md`. Автотесты и реализация ещё должны быть выполнены и проверены владельцами. Для сценариев, затрагивающих обе стороны, integration проверяет серверную часть (исходные данные/ошибки/прежний changes), unit/e2e — фронтовое поведение. Серверный расчёт нового сравнения не предполагается. Эта актуализация статуса не меняет кейсы, Coverage и решение QA, не подтверждает согласование кейсов владельцами или приёмку реализации.
