# Design

## Context

Изменение `compare-model-versions`: отдельное сравнение любых двух различных сохранённых версий одной модели по сценариям [grid-models-09]–[grid-models-32]. Продуктовые уточнения отражены в proposal и дельте spec изменения в sdd-specs.

Стык согласован бэком и фронтом 2026-10-27 по сообщению пользователя «Согласовали твой вариант» и зафиксирован в общем design изменения по его поручению. Повторное ревью QA, тест-кейсы и готовность к реализации этим согласованием не подтверждаются.

## Goals / Non-Goals

**Goals:** определить источник данных, распределение ответственности, правила их интерпретации, обработку ошибок и принадлежность результата выбранной паре.

**Non-Goals:** новый API сравнения, изменение правил загрузки и проверки моделей, прежнего сравнения при загрузке или переходов статусов; внутреннее устройство приложений, объединение версий и экспорт отчёта.

## Decisions

### 1. Контракт и место вычисления

Контракт без изменений, версия 1.0.0: `sdd-specs/contracts/grid-models-api.yaml`, OpenAPI 3.1. Новые операции, поля и коды ответов не вводятся; повышения info.version нет.

Источник данных — `GET /api/grid-models/{id}`, успешный ответ `200 Model`. Модель содержит `versions`, каждая версия — `id`, `number`, `status` и исходный `document.objects`. Документы доступны во всех предусмотренных статусах, включая неопубликованные версии. Наличие опубликованной версии и общая база для отдельного сравнения не требуются.

Фронт вычисляет отдельное сравнение выбранных документов. Бэк передаёт сохранённые значения, включая ошибки объектов и порядок массивов. Операция скачивания опубликованной версии для этой функции не используется.

Серверное вычисление рассмотрено как альтернатива и в это изменение не входит: необходимых данных достаточно в текущем ответе. Появление новых потребителей результата или неприемлемая отзывчивость потребуют отдельного согласования стыка и, при изменении API, версии контракта.

### 2. Ответственность участников

| Участник | Ответственность |
|---|---|
| Бэк | Доступность документов всех статусов; сохранение значений и порядка массивов в ответах; существующие ошибки API; сохранение прежнего сравнения при загрузке. Автотесты своей части — после получения кейсов QA. |
| Фронт | Допустимость выбранной пары, вычисление отдельного сравнения, значения «было → стало», предупреждения о неполноте, получение необходимых данных, повтор и защита от запоздавших результатов. Внутреннее представление результата и устройство UI определяет владелец фронта. |
| QA | Повторное ревью требований и стыка, подготовка тест-кейсов и назначение владельцев автоматизации. |
| Владелец sdd-specs | Фиксация согласованного общего design в хранилище и последующее ведение карты фичи. |

Выбранная пара на сервер не передаётся: проверки пары выполняет фронт. Это не меняет серверные проверки операций записи, согласования и публикации.

Уточнение BACK-01 уже принято пользователем и зафиксировано в `sdd-backend/openspec/changes/compare-model-versions-back/review-notes.md`: submit версии draft с непустым issues, актуальной revision и существующей организацией возвращает `409 invalid_transition` с сохранением документов, issues, статусов и остального состояния модели. Ожидание соответствует [grid-models-28.1]; текущая реализация, по замечанию бэка, возвращает `400 validation`, исправление и подтверждающий автотест ещё не выполнены. Формат Error и перечень HTTP-ответов уже есть в контракте 1.0.0, файл контракта не меняется. Коды остальных ошибок и поведение approve/publish этим решением не переопределяются.

### 3. Идентификация пары и источник значений

Пара определяется `(modelId, beforeVersionId, afterVersionId)`. Обе версии должны находиться в `versions` одной Model и иметь разные `id`. Номер версии служит для показа пользователю и не заменяет идентификатор. Направление не выводится из времени создания или `baseVersionId`.

Для вычисления используется `Version.document`, а не `Version.changes`: последнее остаётся результатом прежнего сравнения с опубликованной базой. Отдельное сравнение не записывает данные, статусы, ревизию или историю действий.

Сравниваются поля объектов `name`, `type`, `voltageKv`, `links`. Метаданные версий и порядок объектов не участвуют в определении различий. Неизвестные типы, недопустимое напряжение и несуществующие ссылки сравниваются как сохранённые значения без исправления; наличие `issues` само по себе не означает неполноту результата.

### 4. Точное сопоставление и исключения

- Непустые ID и строковые значения сравниваются точно, с учётом регистра, без обрезания пробелов и нормализации. `line-1` и `LINE-1` — разные ID. Значения для показа сохраняются без преобразования.
- Пустым считается ID нулевой длины либо состоящий целиком из символов набора Unicode White_Space. Это правило используется для отдельного сравнения и не меняет прежнюю проверку загружаемых данных.
- Напряжение сравнивается как число без допуска: `110` и `110.0` равны. Форматирование при показе не должно скрывать обнаруженное различие.
- Связи сравниваются как последовательность строк: значимы длина, значения и позиции. Сортировка и удаление повторов перед сравнением не выполняются.
- Объекты с пустыми ID исключаются; количество таких объектов указывается отдельно для каждой затронутой версии.
- Повторения остальных ID определяются отдельно в каждой версии. Объединение повторяющихся ID исключается из обеих версий; каждый исключённый ID указывается в перечне один раз.
- Для оставшихся объектов ID только в «Стало» означает добавление, только в «Было» — удаление, в обеих версиях — сравнение четырёх полей. Смена ID означает удаление и добавление.
- Непересекающиеся наборы уникальных ID дают добавления и удаления. Отсутствие совпадающих ID само по себе не является отсутствием объектов для сравнения.

### 5. Полнота и сообщения результата

| Условие | Сообщение и результат |
|---|---|
| Исключений нет, различий нет | «Различий нет», списки добавленных, удалённых и изменённых объектов пусты. |
| Есть исключения, оставшиеся объекты не различаются | «В однозначно сравнимой части различий нет», предупреждения и сведения об исключениях сохраняются. |
| После исключений в обеих версиях не осталось объектов | «Нет объектов для однозначного сравнения», предупреждения и сведения об исключениях сохраняются. |
| Есть однозначно определяемые различия | Показать их в выбранном направлении; при исключениях одновременно показать предупреждения и сведения об исключениях. |

Для повторяющихся ID используется предупреждение «Результат сравнения неполный: есть объекты с повторяющимися ID» и список исключённых ID. Для пустых ID — «Результат сравнения неполный: есть объекты с пустым ID» и количества по версиям. При наличии обеих причин показываются оба предупреждения. Общий вывод «Различий нет» при неполном результате не используется.

### 6. Получение документов, ошибки и смена выбора

Разрешено использовать уже успешно загруженную Model с полными документами обеих версий: содержимое сохранённой версии неизменяемо, обязательного запроса при каждом запуске нет. Если документов не хватает, сначала требуется успешное получение Model. Отсутствующие данные не заменяются пустым документом. Если выбранной версии нет и после получения Model, сравнение не выполняется; пользователю предлагается обновить данные и выбор.

Сохраняется предел ожидания UI-запроса 10 секунд. Существующий формат ошибки API — `{code, message}`: для отсутствующей модели `404 not_found`, для недоступного хранилища `503 unavailable`. Ответ с документами и ошибками проверки объектов является успешным получением данных.

Ошибка API, сети или таймаут при получении данных выбранной допустимой пары отображается как «Не удалось выполнить сравнение» с действием «Повторить». Повтор относится к текущей допустимой паре; при успехе показывается её результат. Ошибка получения данных отличается от неполноты и отсутствия различий.

При смене модели, любой версии пары или направления прежние результат и ошибка убираются. Поздний результат или ошибка прежнего запуска не подменяет текущий выбор, в том числе когда пользователь успел вернуться к ранее выбранной паре. Механизм обеспечения этого поведения относится к внутреннему design фронта.

Недопустимая или незавершённая пара не запускает сравнение и получение данных ради сравнения. Обычная загрузка карточки этим не ограничивается. Причины выбора показываются по spec:

- Менее двух сохранённых версий: «Для сравнения нужны две версии одной модели».
- Незавершённый выбор: «Выберите версии «Было» и «Стало»».
- Одинаковые версии: «Выберите две разные версии».
- Версии разных моделей: «Можно сравнивать только версии одной модели».

### 7. Прежнее сравнение при загрузке

Прежнее сравнение с базовой опубликованной версией сохраняется отдельно: перестановка тех же связей не считается изменением, при повторяющемся ID используется первый объект. Поле `Version.changes` не переопределяется результатом новой функции. Различие правил является подтверждённым решением PO и проверяется по [grid-models-31] и [grid-models-32].

## Развёртывание (Kubernetes)

Новые переменные окружения, порты, тома, сервисы и миграции для согласованного стыка не требуются. Доступ к API — по относительному пути `/api/...` через существующее проксирование.

## Risks / Trade-offs

Документ ограничен 1000 объектами, но суммарное количество версий модели и связей этим лимитом не ограничено. Согласование вычисления на клиенте не является результатом измерения производительности: отзывчивость проверяет владелец фронта.

Два режима сравнения имеют разные правила по связям и повторяющимся ID. Для нового результата используются документы, для прежнего — существующее поле `changes`; сохранность обоих режимов требует регрессионной проверки.

## Следующий этап

Согласованный стык зафиксирован в этом общем design. QA подготовил `test-cases.md`: 50 кейсов для 24 сценариев; результат повторного ревью требований и стыка отражён в Gaps, кейсы переданы на ревью владельцам приложений. Локальные планы `compare-model-versions-back` и `compare-model-versions-front` созданы, общая карта фичи ведётся в `tasks.md`.

Следующие шаги — завершить ревью кейсов, реализовать локальные планы начиная с автотестов, проверить результат на стенде и пройти приёмку. BACK-01 разрешён на уровне решения, но его исправление и проверка остаются задачей бэка. Историческое `qa-review.md` сохранено; наличие документов не подтверждает выполненную реализацию или согласование за другую роль.
